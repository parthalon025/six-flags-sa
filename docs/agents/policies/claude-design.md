# Claude Design is where this app's front end is designed

**Claude Design is the design surface for `apps/party-tracker`. When a Design project is
introduced, it is a description of what the app should be — reconcile it into the code. Do not
archive it, screenshot it, or admire it.** The owner designs the front end there; a Design project
arriving in a session is a work order, not a reference image.

That is the whole rule. The rest of this file is what it takes to do it without shipping a
prototype's mistakes into a real app.

## Which side is the truth

**Claude Design is canon for what it specializes in.** Inside its own subject — how the front end
looks and reads: structure, layout, hierarchy, spacing, copy, information architecture, and what
an interaction is *for* — the design is the authority and the code conforms to it. That is not a
negotiation between two opinions. If the app disagrees with the design about how a screen is laid
out, **the app is wrong and gets changed.**

Do not argue a design decision back on taste, familiarity, or "the current code does it this way".
The owner designs the front end in Claude Design; that is where those calls get made.

The repo is canon only for what a canvas structurally cannot know:

- **The data model.** What a real party code looks like, what a venue actually contains.
- **The permission model.** Who is allowed to change what; `lib/core/state.js` is the authority.
- **Token *values*.** The design owns which token a thing wears; `globals.css` owns what that
  token resolves to.
- **Accessibility floors.** Contrast is measured, not judged — this app is used in direct sun.
- **Every state a flat prototype never drew** — empty, offline, no-fix, error, mid-sync.

So the honest reading of a disagreement is almost always: *the design is right about the intent
and wrong about a detail it had no way to see.* Build the intent; fix the detail against the code.
The one case where the design is simply wrong is when it contradicts itself — see
[prototype wiring](#what-a-prototype-gets-wrong-every-time) below.

A Design canvas is generated from a moment in the repo's life and drifts from it immediately.
Ours already had, on arrival: its screen map named a `WorldPicker.jsx` that did not exist, its
`--cat-*` colour tokens were invented, and its `judge()` was a lossy copy of `lib/eligibility.js`.
**Verify every path and every token against the code before you build to it** — that is checking
the design's *facts*, not overruling its *judgement*.

Drift runs both ways, so the twin is generated rather than drawn: `npm run design:twin` rebuilds
it from the running app, and `npm run design:push` puts it back in front of the designer. A
hand-kept mirror is a mirror that lies.

## What a prototype gets wrong, every time

These are not hypotheticals. Each was in the first import and each would have shipped:

- **Fabricated data.** A party code `PB-4K9T` in a format `lib/core/ids.js` cannot produce. A
  `Search 100+ Worlds` placeholder over a four-venue manifest. A hard-coded `Location on` badge
  that lies on the manual-pin path. Gate every one on real state or leave it out.
- **Invented tokens.** Colours that exist in the canvas and nowhere in `globals.css`. Map them to
  the nearest real token; never add a colour to satisfy a mock.
- **Handlers wired backwards from their own labels.** The gate's `I'm ready` skipped location
  while `Browse Worlds` enabled it, contradicting the mock's own step framing. When a prototype's
  wiring contradicts its label, the label is the intent and the repo's existing handler is the
  implementation.
- **A permission model it does not know about.** The canvas let anyone edit any member's height;
  `lib/core/state.js` silently drops that patch for a device-holding peer. Following the mock
  builds a control that animates, updates local state, and reverts on the next snapshot.
- **Contrast that fails outdoors.** The canvas is rendered on a desktop monitor; this app is used
  in direct sun. Measure. Three pairings from the first import were under AA.

## Absence is not removal

A prototype draws the happy path. It will be missing your empty states, error states, offline
states, permission prompts, and half your features. **The absence of a thing in a mock is not a
request to delete it** — restyle it into the new idiom and say what you kept. Ours shipped a
`Not yet in the twin` list naming six features it had simply never drawn.

When a design genuinely does remove something, the cost is real and gets stated, not smoothed
over: dropping the glance rail moved nearest-restroom off the resting screen and `grandma.mjs`
went 47/48 → 45/48. That number stands. Never weaken a check to protect a score.

## The map is not a design surface

`apps/party-tracker/public/venues/*` and the map drawn from it are generated by the venue builder
([builder ↔ app contract](./builder-app-contract.md)). A canvas will contain a hand-drawn park
map because a prototype needs *something* to stand on. It is scenery. Redesign the chrome that
floats above it; leave the cartography to the factories.

## The bundle is how the next round starts closer

`docs/design/system/` is a generated design-system bundle — tokens parsed from `globals.css` in
both palettes, map skins derived through `mapPaint()`, the real glyph set from `Icon.jsx`,
vocabulary from `CONTEXT.md`. `npm run design:build` regenerates it; `npm run design:check` fails
when it drifts, and is wired into the Gate tier.

**Everything in it is derived, never transcribed**, because a transcribed value is a future lie.
That property has already paid for itself: comparing `--peek` in `globals.css` against
`SHEET_PEEK_PX` in `lib/sheet.js` caught a 308-vs-236 drift that no test failed on.

Push it to a Design project so the next design starts from real tokens rather than a guess.
`DesignSync` cannot authenticate in a remote session — `/design-login` needs a real terminal — so
that push happens from the owner's machine. See
[WORKING-WITH-CLAUDE-DESIGN.md](../../design/WORKING-WITH-CLAUDE-DESIGN.md).

## Doing the work

An import is wide, not deep: many screens, each shallow, mostly independent. Fan it out across
agents by screen group, and settle the cross-screen decisions **once, centrally, before anyone
edits** — shared classes are where parallel agents collide, and four local overrides of the same
rule is worse than one considered change.

Then hold it to the same bar as any other change: a guest-visible interaction owes a functional
check and a `critical-paths.json` row ([vertical e2e](./vertical-e2e.md)). The first import missed
that on its own headline feature, and only a standards review caught it. A redesign is not exempt
because it is "just UI" — it is the part the guest actually touches.
