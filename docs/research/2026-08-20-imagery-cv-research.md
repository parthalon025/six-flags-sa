# Imagery-Extraction Tooling — Research Note

Scope: tooling architecture for deriving Map-factory truth/evidence and Visual-factory grounding data from open aerial + street-level imagery, under the decided contract (deterministic passes may write truth above a confidence bar; everything else enters an evidence graph as claims resolved by corroboration or steward review), CPU-only CI, no API fees (subscription Claude/Gemini via an agent-brief file seam), free/open tools only, sha256-pinned + license-gated shipped bytes (AGPL rejected), certified passes deterministic/seeded, registry rows carry adopt-triggers.

---

## 1. Three-lane extraction architecture

The lanes map directly onto the evidence-graph contract, and — independently — onto the write-gate the OSM community has already enforced for exactly this problem (imagery → map data) for over a decade (§4). No lane gets a "confidence is high enough" exception to that gate; only **determinism** does.

### Lane A — Deterministic CV (classical, no/seeded RNG)
- **OpenCV/scikit-image primitives with no internal randomness** — Canny, `findContours`, marker-given watershed, template matching, GLCM/LBP texture descriptors, VARI/ExG/GLI band arithmetic, SLIC superpixels. All confirmed RNG-free by source/doc read.
- **May write:** Map-factory truth directly, above the confidence bar, *when the specific invocation is proven deterministic* — i.e. an output-hash CI check shows two consecutive runs on the same input are byte-identical (needed because thread-count and SIMD/IPP variance can silently break "no RNG" determinism even without k-means in the loop — CV-dump §8.3–8.4).
- **May not write truth for:** any step that routes through `cv2.kmeans` or `cv2.grabCut` (GrabCut's GMM init hard-codes a `KMEANS_PP_CENTERS` call with no exposed seed control — CV-dump §1/§8.1) or through RANSAC-based homography fitting (`findHomography`/`findFundamentalMat` are documented insensitive to `cv2.setRNGSeed()`, opencv/opencv#24835 — CV-dump §6/§8.2) unless the mitigations in §2 are in place and CI-verified. Until then, these outputs are evidence-graph claims like any other lane.

### Lane B — Pinned-model lane (CPU-viable ONNX inference)
- DeepForest (tree crowns), MobileSAM/EfficientSAM (segmentation), Tesseract (signage OCR), TorchGeo backbones (land-cover features).
- **May not write truth directly, ever, by default** — the ONNX format does not fix floating-point operation order, so results vary across onnxruntime versions, BLAS backends, thread config, and even pip-vs-conda-vs-source builds of the *same* version (obj-dump §8, citing randomascii.wordpress.com and arXiv:2506.09501v2). Pinning the package version is necessary but not sufficient for bit-exact reproducibility. Treat as "reproducible within a tolerance," which fails the "deterministic/seeded" bar for a certified pass.
- **Writes:** evidence-graph claims only, resolved by corroboration (agreement with a Lane A pass or a second model) or steward review — this is also the shape DeepOSM and RoboSat converged on independently (geo-dump §3): model output is a *candidate layer*, reviewed/deduped before anything touches the accepted graph, never auto-applied.

### Lane C — Agent-vision lane (subscription Claude/Gemini via agent-brief file seam)
- Structured-output vision calls (forced `tool_choice` / JSON-schema-constrained response) for semantic reads a classifier can't do cheaply: object-type disambiguation, damaged/angled signage text, tree-vs-shadow edge cases, and — separately — the Visual-factory grounding harvest itself (real roof colors, path materials, lawn tones per venue).
- **May not write Map-factory truth, ever** — non-deterministic even at low/zero temperature (obj-dump §9), external network dependency, per-call cost. Map-factory output from this lane is always an evidence-graph claim, same review gate as Lane B.
- **Visual-factory role is different in kind, not just degree:** grounding harvest (palette/material extraction) isn't a geometric "certified pass" candidate at all under the constraints given — it's reference data feeding kit palettes and material assignment. Lane C is the *primary* tool for that harvest (this is inherently a perceptual/semantic judgment task, not a geometric-extraction one), but low-confidence reads should still route to steward review per the recommended mitigation (obj-dump §9: emit a confidence field, route low-confidence to human review rather than trusting full automation — reported 95–98% accuracy on structured-extraction analogs, with 0.5–2% schema-validation failures even under strict prompting).

**Net rule:** a claim earns a direct Map-factory truth write only by being Lane A *and* CI-proven deterministic on that exact invocation. Every other output — Lane A-but-RNG-tainted, all of Lane B, all of Lane C for Map-factory purposes — is an evidence-graph claim awaiting corroboration or a steward. This is stricter than "high confidence," and it mirrors the OSM community's own rule below almost exactly.

## 3. NAIP / Mapillary access recipe (open-data paths)

### NAIP
- **Legal basis for automated extraction:** NAIP is a US federal government work → public domain in the US. OSM's "no tracing from copyrighted maps" rule doesn't apply; algorithmic/CV extraction from NAIP is unambiguously legal with no special grant needed (geo-dump §1). This is the deciding factor for restricting Lane A/B derivation to NAIP+3DEP+Sentinel-2+Mapillary and rejecting Google/Bing/Esri basemaps for derivation (§5).
- **AWS Open Data Registry** (region **us-west-2** only), three buckets — **all Requester Pays, not anonymous** (real AWS credentials required despite in-region transfer being free):
  - `naip-analytic` — 4-band (RGB+NIR) MRF and COG, lossless, Esri-processed.
  - `naip-source` — 4-band uncompressed raw GeoTIFF, no overviews.
  - `naip-visualization` — 3-band (RGB) COG, YCbCr JPEG q85 — practical choice for quick display/extraction.
  - CLI: `--request-payer requester`; GDAL `/vsis3/`: `AWS_REQUEST_PAYER=requester` plus real `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` — no `AWS_NO_SIGN_REQUEST` anonymous path exists for these buckets (geo-dump §2, citing rasterio issues #692 and #2061).
  - Coverage 2010–2023 (ongoing), ~1 m GSD generally (0.5–2 m depending on product/state), horizontal accuracy within 6 m of ground control.
- **Genuinely no-auth alternative — Microsoft Planetary Computer.** `naip` STAC collection, anonymous short-lived SAS token from `https://planetarycomputer.microsoft.com/api/sas/v1/token/naip` (~45 min expiry), `planetary_computer.sign()` Python helper auto-signs STAC Items/Assets — no account or subscription key. **Preferred path if AWS credential management is unwanted** (geo-dump §2).
- **Windowed reads:** rasterio `Window(col_off, row_off, width, height)` avoids loading the whole quarter-quad COG; GDAL/rasterio still reads whole internal tile-chunks per request (e.g. 512×512), so batch/align windows to COG internal tiling for efficiency (geo-dump §2).
- **Band structure for NDVI viability:** modern NAIP acquisitions are 4-band RGBN; older archive imagery may be RGB-only. Prefer standard NDVI whenever the 4-band asset is available; fall back to VARI/ExG/GLI (Lane A, §2) for RGB-only crops (older vintages / non-NAIP orthophotos) (CV-dump §3).

### Mapillary
- **Imagery license:** raw contributed imagery is CC BY-SA 4.0 (changed from CC BY-NC in 2014) — Terms of Use / Commercial Terms at mapillary.com/terms and mapillary.com/commercialterms (obj/geo-dumps).
- **Commercial use of API-derived detections** is permitted specifically for (i) improving/training/developing your own products/services/datasets/algorithms and (ii) providing services on behalf of clients — attribution (visible Mapillary logo + link back) required for this general commercial path (obj-dump §6).
- **OSM-specific carve-out** (separate and broader than the general commercial terms): Mapillary grants OSM contributors "the right to use any Mapillary image for editing and deriving metadata for the purpose of contributing content to OpenStreetMap" — street numbers, signs, names, building descriptions, road conditions. Derived metadata may be published directly to OSM under OSMF contributor terms, or published elsewhere under ODbL. Attribution here is "appreciated," not strictly mandated (geo-dump §1).
- **Excluded:** the separately-downloadable static "Mapillary Traffic Signs Dataset" has an unresolved commercial-licensing question on Mapillary's own community forum — do **not** assume it carries the same CC BY-SA/API terms; verify with `support@mapillary.com` before commercial reuse (obj-dump §6, geo-dump §1).

## 4. What the OSM import-guidelines precedent teaches about the evidence-review gate

This precedent is not analogous to our evidence-graph design — it is effectively the same design, arrived at independently by a decade of OSM community enforcement, and it validates the "deterministic-above-bar writes truth, everything else is a reviewed claim" split rather than a confidence-threshold-only split:

- **No ML exception lane, stated plainly:** "If you upload algorithmically generated data without manually verifying the individual features against local knowledge or suitable primary data you are doing a mechanical edit or import and must follow the rules for those" (help.openstreetmap.org, corroborated by the Import wiki page — geo-dump §4). Confidence score is irrelevant to this rule; *verification* is the gate, not model certainty.
- **Rationale, not just rule:** imports get more scrutiny than ordinary edits "because poor imports have significant impacts on both existing data and local mapping communities" — an academic study of OSM bot governance found inadequate review/escalation tooling as the root friction (ACM TOCHI, DOI 10.1145/3665326 — geo-dump §4). This maps to why our contract routes non-deterministic output to steward review rather than a purely automated corroboration threshold: unreviewed automation at scale is where trust breaks, independent of any single pass's accuracy.
- **Conflation is a required, *named* step**, not optional QA — the JOSM conflation plugin and QGIS geometry tools are the standard tooling; it operates on a subject-layer/reference-layer model where a human explicitly matches/merges rather than the tool silently overwriting (geo-dump §4). This is the direct precedent for treating our evidence graph's corroboration step as mandatory infrastructure, not a nice-to-have.
- **Documentation-before-execution requirement:** a written plan covering data-source accuracy, licensing, conversion methodology, conflation approach, attribute→tag mapping, simplification approach, changeset-size policy, QA plan, and an explicit revert plan — before any batch runs (Import/Guidelines, geo-dump §4). Directly supports our registry-row model (tool, license, determinism reality, adopt-trigger) as the equivalent artifact per tool, and argues for an explicit revert/rollback path per registry adoption, not just per pipeline run.
- **JOSM as the review instrument, concretely:** import to local layer → run Validator → manually inspect/fix → upload — never a direct machine-to-server pipe. The related `osmsync` library is described as producing "a JOSM file for human review," i.e. formalizing "generate diff, force a human look, then commit" (geo-dump §4). This is the literal shape of "claims resolved by … steward review" in our contract.
- **RoboSat/DeepOSM operational lessons reinforce the same shape:** RoboSat ships `rs dedupe` specifically to strip predictions duplicating existing accepted data *before* anything nears upload — conflation-against-truth is mandatory post-processing, not optional (geo-dump §3). DeepOSM built a mismatch-*review* mode (renders "model says X, source says Y" images for humans) rather than auto-correcting — the same "flag for human review, never auto-apply" pattern our Lane B/C write-restriction encodes. RoboSat's documented false-positive failure mode (predicting buildings from training-set imbalance) is a direct caution for any Lane B tree/path classifier: structural bias, not incidental noise, is the expected failure shape.
- **SCP's (QGIS Semi-Automatic Classification Plugin) architecture is the closest formal template for human-in-the-loop calibration:** human digitizes training-area ROIs → plugin computes spectral signatures → classification-preview loop where the human checks class-assignment correctness *before* the human accepts a full-image classification run (geo-dump §5). This is a workable template specifically for calibrating Lane A/B classifiers (e.g. surface-class thresholds) with human-picked training examples, distinct from — but complementary to — the steward-review gate on final output.
